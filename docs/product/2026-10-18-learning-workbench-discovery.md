## 对核心需求的理解

工作台需要帮助用户从跟写过渡到独立实现：能够描述一个功能的需求，说明模块与数据的关系，解释关键设计决定，再完成一个小改动。知识整理、原文回查和复习围绕这一过程积累。

新增面试场景后，目标进一步扩展为把所学内容转成可用于面试表达和项目追问的能力。目标覆盖 Agent 应用开发、Python 后端兼 AI 和 Java 相关岗位；具体职级、岗位权重、面试深度和训练方式待确认。既有 Java 工作经验与当前 AI 学习情况分别记录。

工具调用问题中，用户能正确说明“模型先返回工具名称和参数，再由程序执行”。这只支持对该问题的理解，不能据此判断整个项目掌握程度。后续通过具体解释与练习结果记录掌握情况。

### 文字和语音共用的面试流程：设计建议

- 建议流程：选择一个岗位方向及本轮范围 → 逐题回答 → 根据回答追问 → 生成具体反馈 → 关联待复习知识点。文字和语音使用同一套题目与反馈结构，不分别维护题库。
- 文字输入适合整理概念和代码思路；语音输入适合练习口头解释。是否允许在一轮中切换输入方式尚未确认。
- 语音建议先采用逐轮录音、转写、提交，转写结果可检查和更正技术名词，再以确认后的回答进行内容反馈。语音服务或模型出错时保留可重试状态，不将识别错误直接判为知识错误。
- 训练模式可在每题后反馈并按需给提示；模拟面试模式可先提问追问，结束后统一反馈。两种反馈节奏是建议，尚未作为已确认需求。
- 文本内容评价与口头表达评价分开：没有实际分析音频时，不推断语速、停顿、发音或情绪；不从说话方式推断人格或招聘结果。
- 语音播报、打断、实时通话及持续监听不作为已确认功能。当前没有启动麦克风录制、调用语音服务或实际面试。
- 用户已接受优先打通“建立少量题目 → 文字/语音回答与追问 → 面试反馈 → 待复习清单”的顺序；该模块不依赖深造播放器画面。原课程需求和未解决的画面输入问题均保留，工作台底座与首批 Agent 以可用切片逐步实现。

2. **先由用户复述**：说明功能要解决什么问题、实现顺序、数据如何流转。输入负担应小，可先写几句话。
3. **结合真实代码补齐**：呈现调用关系、参数来源、状态变化和关键决定，标明相应文件/函数与课程出处；材料缺失时标明未确认。
4. **完成一个小练习**：围绕当前功能设计一个改动，例如给现有工具新增参数并说明如何传给 Worker；先让用户写思路，再动手。
5. **按需分层提示**：先提示方向，再定位相关代码，再提供骨架，最后由用户主动展开完整参考答案。允许主动跳过；不能因查看过答案就自动标记掌握。
6. **生成复盘记录**：包含重点、实现思路、用户卡点、练习反馈和下次复习内容；工作台预览、编辑后保存在本地，按用户选择保存到语雀。云端处理方向已恢复，具体语雀接入与更新规则仍待设计。

这是课后复盘流程。为取得无字幕课程讲解，已验证一次明确授权的播放器音频采集；是否扩展为看课期间记录播放器窗口画面仍待确认，不假定持续监控整个屏幕或自动操作 PyCharm。练习默认由用户在 PyCharm 中完成；自动运行、修改学习代码不是已确认范围。

## 两种复盘模式

时间档位已由用户选择，具体内容与默认项仍是设计建议：

| 模式 | 建议内容 | 建议结束条件 |
| --- | --- | --- |
| 10 分钟快速回顾 | 复述本次功能；补齐关键调用链；确认少量重点；回答两三个自测问题 | 留下一份简短复盘和待复习卡点；不要求完成代码改动 |
| 20～30 分钟练习复盘 | 在快速回顾基础上，围绕当前功能完成一个小代码练习，按需逐级提示 | 保存实现思路、尝试结果和仍不理解之处；未完成可继续 |

- 建议默认推荐练习复盘，允许随时选择快速回顾；默认项尚未单独确认。
- 两种模式共用同一功能的学习记录，快速回顾后可继续练习，不重复导入材料。
- 复盘时长指用户参与理解与练习的目标时间；视频转写、材料解析与 AI 生成所需等待应单独显示，不承诺包含在该时间内。
- 快速模式的自测与练习模式的代码尝试提供不同证据，均不因阅读总结或展开参考答案自动标为掌握。

## 两种复盘入口

两种入口已由用户选择，共用同一套学习记录、复盘模式和提示流程。以下交互细节为设计建议：

- **辅助选择**：用户主动开始复盘后，工作台比较项目与上次已记录基线的变化，建议少量主题及相关文件，用户选择、修正范围。代码发生变化不等于用户学习或理解了该内容，不据此直接评定掌握程度。
- **手动指定**：用户输入“今天学了什么”，选择相关文件、函数和已有课程材料；即使代码没有变化，也能复盘概念或旧功能。
- 自动建议与手动指定可以组合：先用建议缩小范围，再修改主题、补充材料；不是两套互不相通的功能。
- 首次关联项目时没有上次复盘基线，不能把当前完整项目当作当天学习成果。先按当前项目结构建议候选主题，由用户确认，或直接手动指定。
- 比较范围应考虑用户选择的已提交和未提交变化，具体基线存储方式尚未决定；不能只用最近一次 Git 提交推定本次学习范围。
- 用户确认本次内容后可调用云端 AI；自动建议主题不代表将整个项目无差别发送。上传范围与所选课次、代码和复盘目的保持一致。

## 课程与项目的关联

已确认课程与功能对应清楚。建议以用户现有课程目录作为学习主线：课程下设课次，每个课次可关联相关代码文件、字幕/文字稿、课件和语雀笔记。具体关联由用户确认，项目变化仅辅助建议复盘主题。

- 首次关联课次与材料后保存关系，后续复盘复用已有选择并允许调整，不要求每次重新提供全部材料。
- 一节课内容较多时，允许一次只复盘其中一个功能；同一课次的多个复盘记录保留各自的理解、练习和待复习内容。
- “学过某节课”和“掌握相关知识”分别记录，不能由关联成功或代码有变化直接判定掌握。
- 深造播放器内的在线课程已确认没有字幕；其他本地课程的文字稿覆盖程度、格式，以及是否有可正常导入的音视频文件仍未确认。

### 无字幕客户端课程的输入缺口

- 只关联课程目录、代码、课件和个人笔记时，AI 可以基于这些材料组织复盘，但无法据此恢复老师没有记入材料的口头讲解。生成的补充解释应标为 AI 解释，不能标为老师原话或编造视频时间点。
- 用户已决定第一版必须覆盖视频讲解输入。缺少讲解时可以利用已有材料做部分复盘，但不能将其视为已达到该项需求。
- 早期常见安装位置检索未定位到播放器；用户提供路径后，已确认目标为 x86 PE，导入 Qt 5 Multimedia 等依赖，配套 Qt 库版本 5.14.2.0。主程序自身版本未取到，课程导出能力未知。随后仅执行用户授权的音频采集，没有修改播放器或上传课程。
- 本机 Windows 11 build 26220 满足微软应用音频回环示例的版本前提；建议先验证仅采集播放器进程树声音，不能把系统版本满足条件等同于播放器测试通过。
- 30 秒定向音频测试已在用户明确授权后执行：MainPlayer PID 20408，Windows 进程树回环，实际采集 30.002 秒，音频文件时长 29.97 秒，有非静音信号且无 discontinuity 标记。结果保存在 `analysis/szplayer-input-probe/`。用户已确认讲解清楚且无其他声音；下一步解决视频画面关联，再验证云端转写与整理。
- 建议做一次 3～5 分钟课程片段的可行性验证：取得带时间信息的转写并与画面关联，人工核对技术名词、核心观点和代码关联。用户最新更正允许云端方案，恢复云端转写和 DeepSeek 整理的候选路线，服务选择与实际效果尚未验证。
- 验证优先关注能否稳定取得可转写音频，以及转写是否保留“为什么这样实现”的讲解。只拿到源代码或只生成通用概念总结不算通过。

### 讲解与视频画面的对应：方案建议，待确认和验证

- 当前音频测试只证明能取得讲解；没有同时采集画面，不能事后可靠恢复该片段中老师展示的代码、课件、鼠标位置或视频时间点。
- 推荐将输入验证扩展为“播放器窗口画面 + 播放器音频”的同步记录，再在课后抽取关键帧、生成带时间范围的转写，按统一采集时间轴组成学习片段。此为设计建议，不是已实现能力。
- 应先保留同步记录，再在画面变化、切换课件或代码区域等位置选取关键帧；仅稀疏定时截图可能遗漏代码编辑等中间过程。帧选择效果和文字可读性需要测试。
- 每个复盘知识点应关联讲解文本、对应关键画面、记录内时间范围，并在有证据时关联本地代码文件/函数。老师示例与用户代码可能不同，不能靠相似概念断定版本或行号一致。
- 区分两类时间：录制片段内时间，用于音频、截图与本地回放的对应；原课程播放时间，用于回到深造播放器相应位置。后者在暂停、拖动和变速下不能简单用起点加经过时间推算，需分段记录、识别可见进度或人工校准。
- Windows 官方 Graphics Capture 文档提供应用窗口帧和用于跨媒体同步的系统相对时间戳；这仅支持候选实现路线，不能证明深造播放器能正常采到画面、画面非黑屏或同步精度已达标。
- 画面若不可正常采集，应明确标注缺失，并使用用户可提供的课件、截图与源代码补充，不把音频分析包装成视频理解。

- 候选替代输入为“老师讲解的音频转写 + 本课独立课件 + 老师示例源码 + 用户项目代码”，按课程目录、概念和明确出现的函数/类名关联，生成带来源的复盘。该方案不等于还原原视频中的具体画面、光标或编辑过程，尚待用户确认材料可得性与方案接受程度。
