## 0. 结论先行

1. PRD 的边界纪律很好（候选先检查、来源分型、无总分、原型/真实分离），大部分可以原样保留。
2. 最大的问题不在“范围太大”，而在“第一次能验证价值的时间太晚”：按现有计划，用户第一次真正回答一道题并收到追问，要到 M2 的 Task 10～12，而前面压着工作区隔离、junction、密钥、草稿、安装包等工程门禁。DeepSeek 追问质量这一核心价值风险也被推迟到那时才首次接触真实样本。
3. 第二大问题是“已确认”与“设计默认”的边界在 FR 层不可追溯，并且存在两处记录冲突（MCP 的确认状态、“第一版必须包含视频讲解整理”的后续处置）。
4. 推荐保持 P0 最终承诺不变（含语音、Agent 配置、MCP、共用工作台），只调整里程碑内部顺序、增加一个“可自用试用点”，并给价值验证、质量判断和 AC 的真实/替身口径补上可测定义。

问题分类标记：
- **[缺陷]** 文档内部冲突或缺失，可以直接修正，无需用户取舍。
- **[取舍]** 我的推荐，有替代方案，协调者或实施者可反驳。
- **[待用户]** 涉及已确认需求或产品方向，必须由用户最终选择。

## 1. 应保留的优点

| 优点 | PRD 位置 | 保留理由 |

| 生成与入库分离，候选题必须检查 | FR03、AC03/AC04 | 直接回应“模型输出不能直接成为知识”的风险，且技术方案已有结构校验与操作 ID 支撑 |

| 报告默认无总分、结论需指回回答 | FR07、AC11 | 与“知道具体怎么改”的用户故事 US06 一致；技术方案 §8.2 已把追问依据落实为原文子串 + 偏移校验，可机器验证 |

## 2. 关键问题（9 项，按严重度排序）

严重度口径：高 = 不处理会导致做完 P0 仍无法判断产品是否有用，或导致范围/验收无法收敛；中 = 会造成返工或验收争议；低 = 文档一致性。

### 问题 1 · 价值验证目标与 P0 流程、验收脱节　[缺陷 + 取舍]　严重度：高

**证据**
- §1.3 第二段：验证方向是“不看课程描述一个功能的调用顺序与设计理由，并完成或解释一个小改动；后续回顾时能返回原资料并重新讲清”。这来自探索记录 217 行，是**学习复盘（P1）**的成功标准。
- §1.3 第一段与 §2.3 定义 P0 是面试流程；§8 的 AC01～AC24 全部是功能/可靠性验收，没有一条验证“练习是否有帮助”。§8 末段只说“练习价值需小样本人工核对”，未定义样本、方法和记录位置。
- FR04 题目详情只列“题目、意图、要点、追问与来源”，没有该题的历次作答记录，因此即使想比较“复练前后”，产品内也看不到。

**问题**：P0 能全部通过 AC 却仍无法回答“这个工作台对面试准备有没有用”。验证目标写的是 P1 的事，P0 自己的价值假设没有写出来。

**影响**：单人开发者投入 M1～M3 后，没有依据决定继续投入 M4，还是先调整面试功能；也无法区分“功能可用”和“对用户有帮助”。

**推荐改法**
1. §1.3 拆成两条：P0 价值假设（面试准备）与 P1 价值假设（保留现有学习表述，挂到 §7）。
2. P0 价值假设建议写成可观察行为，不写数字目标：用户用自己的题库完成训练 → 报告里的 gaps 被加入复习 → 间隔一段时间后对同题单题重练 → 比较两次反馈中的 gaps/uncertain 是否缩小，并由用户标注“这次能讲清/仍需补练”。比较依据是两份已存在的报告，不是新指标。
3. FR04 题目详情增加“历次作答与报告链接”（数据已在 Interview/Turn、Review/Attempt 中，属于查询展示）。
4. 新增“试用记录”交付物：`docs/development/acceptance/` 下的人工试用记录模板（题目、两次报告 ID、用户自评、是否借助参考、用户主观备注），不写私人原文。

**可测试验收**
- AC-V1：给定同一道题完成过两次面试，题目详情按时间列出两次作答、对应报告版本和复习自评，均可打开。
- AC-V2：M2 门禁要求至少一份真实（非替身）试用记录存在且字段完整；记录内容是否“证明有用”由用户判断，不作为自动化通过条件。

### 问题 2 · 首个有价值流程出现太晚，前置工程门禁过重　[取舍，部分需用户确认]　严重度：高

**证据**
- §9：M1 退出条件为 AC01～05、19、21、23，只到“题库可存可导出”；回答与追问在 M2（AC06～08）。
- M1 计划 Task 04（工作区、目录授权、junction、文件替换、来源快照）排在 Task 05（DeepSeek）和 Task 06（候选生成）之前；Task 09 门禁还要求在“无 Python/Node 的 Windows x64 环境启动”安装包。
- 接手指南 §5：Task 04～09 均未实现，G01 服务打包缺失。
- PRD §3.2 第 4 步与 FR03 已允许“无资料也可生成主题训练题”，AC03 也是“按主题生成”，说明主题建题不依赖资料链路。

**问题**：用户的首个价值点是“有题可练并得到针对性追问”，但计划先做最重的资料隔离与发行门禁，再接触真实模型。单人开发时，这段时间没有任何用户可感知的产出，也没有真实质量反馈。

**影响**：如果 DeepSeek 在题目质量或追问贴合度上不达预期，问题会在大量基础设施完成后才暴露，返工代价最高。对自用产品，安装包门禁在 M1 阻塞业务验证，收益有限。

**推荐改法**（保留所有 M1 交付物，只改顺序与门禁位置）
1. M1 内顺序改为：Task 05 DeepSeek 配置 → Task 06 的“主题建题”路径（`materials=[]`）→ Task 07 题库 → Task 04 资料与来源 → Task 06 资料路径 → Task 08/09。需 OpenCode 或实施者确认 Task 06 的 `build_context` 与 task create 在空材料时不依赖 Task 04 的表（M1 计划 Task 03 已写测试流程的 workspace 引用暂为 null，看起来可行，但我未核验代码）。
2. M1 门禁中“无开发环境安装包启动”改为 M3 门禁（G01/G04 仍独立跟踪，不删除）。理由：P0 才是发行版本，个人自用的 M1/M2 试用可在开发环境运行。**这一条改变了 M1 计划 Task 09 的现有门禁，需用户确认。**
3. 在 M2 中设一个“可自用试用点”M2a：Task 10～12 的训练模式 + Task 13 的最简报告即可开始问题 1 的真实试用；模拟模式、成果交接（Task 14）、复习（Task 15）、恢复门禁（Task 16）随后完成。M2 的最终退出条件不变。

**可测试验收**
- 新顺序下，M1 中期检查点：未建立任何工作区时，配置有效 DeepSeek 后可按主题生成候选并保存到题库；日志与导出不含密钥（复用 AC02/AC03）。
- M2a 检查点：在开发环境中用真实 DeepSeek 完成一次单题训练，追问的 `basis.quote` 通过技术方案 §8.2 的子串校验，报告可重新打开。

### 问题 3 · 质量风险验证点过晚，且“质量合格”没有判定口径　[缺陷 + 取舍]　严重度：高

**证据**
- §10：DeepSeek 输出质量在“M1 首次真实请求”验证；语音供应商在“M3 集成前”用中文技术名词小样本评估。
- §8 末段：语音准确性、反馈贴合度和练习价值“需小样本人工核对”，没有核对清单。
- 技术方案 §8.2 已明确“结构化校验只能验证引用存在，不能证明追问质量”，即质量判断完全依赖人工，但 PRD 未给标准。
- 接手指南 §5 / 总览 G05：真实 DeepSeek/ASR 均未配置、未验证。

**问题**：产品最核心的价值（题目是否有用、追问是否贴合、转写是否保住技术名词）没有可执行的合格标准，验证时间点也靠后。ASR 供应商未选定且排在 M3，是 P0 完成的外部依赖，却没有提前探查。

**影响**：M1/M2/M3 的 `-Live` 检查容易变成“请求成功即通过”；ASR 若在 M3 才发现中文技术名词识别不可用，P0 收口被阻塞，届时只能改变供应商或交互。

**推荐改法**
1. PRD §8 增加“人工质量核对清单”，按产物分别列出是/否判断项（不设数字阈值，由用户逐条判断并记录）：
   - 候选题：可回答、考察意图与要点一致、来源类型正确、项目衍生题能指回真实文件、无伪造经历。
   - 追问：引用的是本题实际回答、关注原理/边界/取舍/验证之一、不重复已答内容、跳过后不出现“你刚才说过”。
   - 反馈：correct/gaps/uncertain 能指回原话或来源、接受合理替代方案、无总分或人格判断。
   - 转写：用户列出的技术名词（例如本人常用的框架/库名）是否被正确识别，错误是否可在核对步骤中修正。
2. 新增两个不依赖业务代码的探查（spike），结果写入任务明细，不进入正式代码：
   - S1（M1 早期）：用真实 DeepSeek 对一个主题生成少量候选题和一轮追问，按上述清单人工判断。
   - S2（M2 期间并行）：候选 ASR 供应商用用户自己录的技术问答片段评估，产出“选定/不可用”的结论，供 M3 Task 18 直接使用。
3. §10 风险表把 S1/S2 作为对应风险的验证时间点。

**可测试验收**
- 每个里程碑的 `-Live` 证据包含一份按清单逐项填写的核对记录；任何一项为“否”时记录原因，门禁不以“请求成功”替代。
- M3 开始前，ASR 供应商选择已有 S2 记录；缺账号时标“受阻”，与总览口径一致。

### 问题 4 · “已确认”与“设计默认”在 FR 层不可追溯，且有两处记录冲突　[缺陷 + 待用户]　严重度：高

**证据**
- PRD §2.1 只列条件级确认，§2.2 列默认，但 FR01～FR11 每条没有标注来源，读者无法判断哪些可在试用后调整。
- **MCP 冲突**：早期书面设计 §2“用户已确认”第 5 项写“统一工具入口与最小 MCP 接入”；探索记录 13 行写“书面设计中的交互默认、最小 MCP 范围……待整体评审，不是已批准实施计划”；PRD §2.2 把“最小本地 stdio MCP”列为**设计默认**。三处口径不一。
- **视频讲解冲突**：探索记录 46 行“用户明确选择 A：第一版必须包含视频讲解整理……不能把视频讲解输入降为后续再做”；之后 7、29 行用户接受“先做面试，再完善课程复盘”。PRD §2.3 把课程讲解放到 P1，§7 保留了限制说明，但没有写明 46 行的决定已被后续确认替代，读者会认为 PRD 违背了用户确认。
- **提示方式**：探索记录 40 行用户确认的“逐级提示”针对教学；74 行写“教学中的逐级提示与面试中的追问需要区分”。FR05 把逐级提示用于训练模式，属于合理的设计延伸，但未标明是默认。

**问题**：后续评审者（包括本轮多智能体讨论）无法判断某项能否调整，也可能出现“以为能砍、其实已确认”或“以为已确认、其实只是默认”的误判。

**影响**：范围讨论失去依据；两处冲突不处理会在 M3（MCP）和 M4（课程）时重新争论。

**推荐改法**
1. 在 §2.1/§2.2 后增加追溯表：每个 FR 子项标 `用户确认（来源文档+行/日期）/ 设计默认 / 推导`。不需要改动 FR 内容本身。
2. §2.3 或 §10 决策记录补一句：“2026-10-18 探索记录中‘第一版必须包含视频讲解整理’的选择，已由用户随后接受的‘面试先行、课程复盘随后完善’顺序替代；视频讲解需求保留为 P1 承诺，未取消。”**这一条是我对记录先后的理解，需用户确认是否准确。**
3. MCP 的地位请用户在两种口径中二选一：(a) MCP 是已确认 P0 承诺（按早期设计）；(b) “模型与工具管理”已确认，具体是否用 MCP 实现是设计默认。两种都保留 M3 交付，区别只在于试用后能否调整。

**可测试验收**
- 追溯表覆盖 FR01～FR11 每个子项；任一标“用户确认”的条目都能在探索记录或早期设计中找到对应位置。
- 决策记录中视频讲解与 MCP 两条均有明确结论和日期。

### 问题 5 · 通用工作台在 P0 的最小承诺没有用户故事锚定　[取舍]　严重度：中

**证据**
- 用户故事 US01～US09 没有任何一条覆盖自定义 Agent、MCP 工具或通用任务成果；但 FR11、FR07 第 5 条、AC17/AC18/AC20 都是 P0 验收。
- FR07 第 5 条“续聊生成修订稿时先比较，不能覆盖用户手动修改”对应 M2 Task 14（新稿比较）；FR11 自定义 Agent 对应 M3 Task 20（有上限工具循环：6 轮/3 工具/8 次调用，见总计划约束）。
- 探索记录 8 行：用户要求“不能将产品收窄为几个孤立聊天页面”；12 行：六项底座已确认，其中第 3 项是“Agent 配置与切换”。
- 技术方案 §10.1：内置流程已有 `agent_config_versions`，M1 Task 05 已创建内置记录。

**问题**：共用工作台是已确认方向，不能删；但 P0 中“通用任务”到底为面试准备解决什么问题没有写出来，导致 Task 14/20 的验收只能测机制（版本、比较、权限交集），测不到用途。

**影响**：通用能力容易按“像 WorkBuddy”去扩展，单人开发的 M2/M3 工作量膨胀；或者反过来，被当成可砍项。

**推荐改法**（不删除任何已确认能力）
1. 增加 US10：“我把一份 JD 或个人项目说明交给一个自定义整理 Agent，得到可编辑的 Markdown 成果，再一键交给面试题整理”。这把 FR07 成果、FR11 自定义 Agent、§3.3 成果转题三者串成一个面试准备场景，也满足“不是孤立聊天页”。
2. US11（可选）：“我配置一个本地只读 MCP 工具（例如读取我选定的笔记目录），让自定义 Agent 引用其结果”。
3. FR07 第 5 条的“续聊修订稿比较”保留，但 P0 验收可以限定为“新稿另存版本 + 并排查看 + 用户选择保存哪一版”，不要求逐段合并。这是对实现深度的取舍，不改变 FR 文字承诺。

**可测试验收**
- AC-G1：创建一个只允许一个只读工具的自定义 Agent，输入一段粘贴文本，得到 Markdown 成果；执行“继续整理成题目”后生成候选批次，原成果版本不变（覆盖 AC18、AC20 的用途场景）。

### 问题 6 · 面试定位缺少目标职级与个人经历输入　[待用户]　严重度：中

**证据**
- 探索记录 30、203 行：实际职责、目标职级、岗位训练比重、简历/JD 导入、各岗位训练深度“仍待确认”。

### 7.1 逐项意见

**1. 早期质量样本与打包门禁 —— 部分接受，并对门禁关系补一条澄清**

- 同意不重排 Task 05～07，Task 04 的目录授权、路径检查与来源快照一项不删。我第一轮的重排建议撤回：M1 计划 Task 06 消费 MaterialVersion、Task 03 的 create 带 `material_version_ids`，先做主题路径再补资料路径确有返工可能，收益不抵风险。
- 保留的最小方案只有 S1：用户自己的 DeepSeek 密钥，一次性探查脚本放在 `output/` 等忽略目录，不进产品代码、不进库；输入只有岗位/主题，不发送任何本地资料；记录候选题和一轮追问，按问题 3 的人工清单判断。它不依赖 Task 04/05 的实现，也不受打包门禁阻塞。注意：这仍是一次对外网络请求，需要用户本人执行或明确同意。
- 发行风险：同意“早期一次 onedir + Forge resources + 安装后握手”探针（即 G01 的最小闭环），正式干净机验收保留到 P0。
- **与既有门禁的关系必须写明**：M1 计划 Task 09 Step 3 现在要求“生成安装包，在无 Python/Node 的 Windows x64 环境启动”作为 M1 门禁。协调者的方案等于把它拆成“M1：开发机上的 onedir 探针 + 握手”和“P0：干净机完整验收”，**这改变了已写入计划的 M1 门禁，需要用户确认**；若用户不确认，则维持原 M1 门禁，S1 照常进行（S1 本来就不受它影响）。

**2. 资料上限与 token 预算 —— 同意改判为“分层上限并存 + 交互缺口”，不是数值冲突；行范围有条件地属于 P0**

- 不是冲突：200 KB/1 MB 是导入与快照的硬上限（技术方案 §6.1），24000/8000 是单次发送的应用预算（§6.3 第 3 条），PRD FR02 已写“发送前还按实际模型输入预算检查，不能因原始文件小就跳过”。OpenCode I3 标“确定缺陷（数量级不一致）”过重。
- 真实缺口有两处：(a) 技术方案 §6.3 第 2 条“向外发送前显示实际材料清单和估计量”没有进入 PRD 与 AC01；(b) 预算不足时的出路。
- 行范围不是可选优化。按 §6.3 第 4 条，没有官方 tokenizer 时用 UTF-8 字节数作保守上界，单个文件达到约 19 KB（24000×0.8）就可能整份无法发送；“去掉文件/分批”对**单个大文件**无效。因此 P0 必须提供“发送单个超预算文件的一部分”的途径。行范围是最简单的实现，技术方案 §6.2 的 locator 已是起止行；若 S1 证实官方 tokenizer 可用且估计显著放宽，可再评估是否降级。
- 最小方案：PRD FR02 增加“提交前显示材料版本、大小与估计量（标‘估计’）；超预算在本地阻断，提供移除/选行/分批”；AC01 增加“超预算 0 次供应商请求”。OpenCode 的 4 档材料测试可保留为自动化用例，其中“1,200 tokens/题”等数值仍是待 S1 实测的建议值。

**3. 追问上限 —— 同意**

PRD §2.2“面试”行写“……每题最多 2 次追问；均为软目标”，与下一行“最多次数为上限”和技术方案 §8.2“本地约束次数、次数超限不发布该追问”冲突，属确定的措辞缺陷。改为：时长与主问题数是软目标；每题追问次数是本地强制的硬上限（可在开始前配置，开始后随快照冻结，见 UI 说明“后改默认设置不改变已开始面试的追问上限”）。AC06/AC07 增加“达到上限后模型建议的追问不被发布”。

**4. 价值验证 —— 同意协调者方案，并修正我第一轮的方法**

- 我第一轮提出的“同题前后 gaps 比较”确有诱导背答案的问题（我自己在 §5 第 4 问也提出过），这里放弃把它作为判断依据，降为“同题历史回看”的展示功能。
- 推荐组合：同题历史回看（问题 1 的 AC-V1）+ 不同角度迁移题（对同一知识点/考察意图让面试题整理 Agent 生成换角度候选，仍走检查入库）+ 用户自评 + 用户对照来源独立核对。判断由用户做，系统只保证记录可回看。
- 不接受 OpenCode §5.3 的“10 场、2 名盲评、≥95%”作为门禁：单人自用没有第二名评审，且这些阈值无依据。保留其中可自动化的部分：固定的同义表述夹具（AC29a）和 `next_action` 目标可解析（AC29c）。人工 rubric 作为每个里程碑一份的核对记录，不设通过阈值。

**5. queued → interrupted —— 同意，补一个实现细节**

- 核对代码：`recover_startup` 把 `running/cancelling/queued` 都标为 interrupted，`close()` 正常退出时也调用它；与技术方案 §5.4 一致，是有意设计，不是副作用。缺陷只在 PRD FR09 的“活动执行标记中断”措辞，应改为“未完成的排队与执行任务均标中断；等待用户的检查点保留”。
- 同意明确的恢复按钮、不自动重发、不新增批量恢复。补充：`_requeue` 给恢复的任务分配 `max(queue_order)+1`，即按用户点击恢复的先后重新排队，**原排队顺序不会自动保留**。最小方案是 UI 按原 `queue_order` 列出中断任务，并提示“按点击顺序重新排队”；不改代码。
- OpenCode I6 的 `waiting_reason → 业务命令` 映射表有价值，但属于技术方案/M2 计划的补充，不是 PRD 缺陷。

**6. 工具审批 —— 同意 OpenCode 标题过严**

技术方案 §10.2 允许“已有任务授权能覆盖具体对象/动作”时直接执行，超出才持久化 pending proposal。“写工具逐次审批”会让授权覆盖规则失效。最小方案：PRD FR11 写“工具目标、参数、服务配置或风险等级超出已授权范围时须重新确认；确认绑定 task/run/tool/args_hash/config_revision，不跨任务复用”。AC30a（未授权写入 0 次调用）、AC30b（参数/配置变化后旧授权失效）保留。对 AC30c“重启后 pending approval 失效”我持部分异议：技术方案是持久化 proposal 并在取得槽时重新验证配置、范围与 args_hash，重启后只要校验仍通过，保留待确认项比强制作废更符合“重开接着做”；作废只发生在校验不通过时。

### 7.3 回应 OpenCode 的反问

1. **AC24 替身是否有意作为 P0 条件？** 我认为不是有意，而是措辞缺陷：§2.3 要求“真实功能验收”，技术方案 §12.2 要求 skipped 不算通过，二者一致，只有 AC24 例外。按 D3 拆分。
2. **“第一版必须包含视频讲解整理”是否仍有效？** 现有记录不足以下结论。我第一轮写“已被替代”是过度推断，已撤回。由用户在 D13 选择。
3. **queued → interrupted 是预期还是副作用？** 是预期：技术方案 §5.4 明文规定，`close()` 也调用 `recover_startup`。“重开后接着练”在产品上主要指面试的 waiting_user 检查点（保留），而不是排队中的生成任务。建议 PRD 改措辞，不改代码。
4. **200 KB/1 MB 与 24k/8k 如何共存？** 分层并存：导入上限管快照，发送预算管单次请求，以发送预算为最终判断。是的，应在提交前显示可发送量，而不是生成时才失败（D4）。8k 输出是否够 10 道，交给 S1 和 M1 Live 实测，技术方案 §7.3 已规定不足时显示实际数量、不假称 10 道。
5. **报告只要能指回依据就算达标吗？** 不够。引用存在只说明原话存在（D9 的 `quote_verified`），“遗漏”属于模型判断。最小可测部分是固定同义夹具和 next_action 可解析；质量判断是每个里程碑一份人工核对记录。一个样本不够统计意义，但单人项目也不应设盲评阈值门禁。

### 7.4 剩余异议

- **OpenCode I2 的发行要求**：本机自用阶段的代码签名与“3 次干净 VM”不应是 P0 门禁。建议 P0 干净机验收 1 次并记录环境；签名在对外分发前处理（技术方案 §14 已写“对外分发前”）。
- **OpenCode §5.3 量化目标**：除“0 次静默截断、超预算 0 次请求、取消后 0 次上传”这类可二元判断的项外，其余百分比阈值缺少依据，不应写进 PRD。
- **OpenCode I4 第 3 条“本次上传审计条目”**：同意记元数据，但应复用现有任务事件（同事务事件已在 T005 实现），不另建审计表。
- **对协调者第 1 条的提醒**：S1 是向外部服务发送内容，即使只有主题，也属于需要用户本人执行或同意的动作；不能由智能体在没有账号授权的情况下代为执行。
- **对协调者第 5 条的提醒**：“保留队列顺序”在当前代码下只能通过 UI 提示实现，若用户要求严格保留原顺序，就需要改 `_requeue` 的排序逻辑，那是一次小代码变更，不是纯文档修改。
